# Sage — chat UI

A React front end for Sage, built on [assistant-ui](https://www.assistant-ui.com/).

The interesting thing about this directory is how little of it we wrote. Three files are ours; the
thread, composer, streaming render, markdown, auto-scroll, cancellation, and keyboard behaviour all
come from the library. Chat plumbing is not what Sage is for.

## Running it

Needs the API running alongside it:

```bash
# terminal 1 — the API, from the repo root
uv run poe dev

# terminal 2 — this
npm install
npm run dev          # http://localhost:5173
```

| Command | Does |
|---|---|
| `npm run dev` | Dev server, proxying `/chat` to the API |
| `npm run build` | Typecheck (`tsc -b`) then bundle |
| `npm run lint` | oxlint |

## The three files we own

Everything else under `src/components/` was generated by `assistant-ui init` and is maintained
upstream.

**[`src/lib/sage.ts`](src/lib/sage.ts)** — Sage's HTTP contract, and the only place that knows it.
Speaks `POST /chat/stream`, parses the SSE frames, and yields text. Above this file the app deals in
`{ role, content }` and never in status codes.

**[`src/lib/sage-adapter.ts`](src/lib/sage-adapter.ts)** — a `ChatModelAdapter`, which is how a
question reaches Sage. assistant-ui messages carry an array of parts; Sage takes a string. The
flattening lives here so the API never has to learn a richer message shape than it needs.

**[`src/lib/local-history.ts`](src/lib/local-history.ts)** — a `ThreadHistoryAdapter`, which is where
the conversation lives between reloads. The library calls `load` once when the thread mounts and
`append`/`update` as messages settle, so "read on load, write on reply" needs none of our wiring.

[`App.tsx`](src/App.tsx) hands both to `useLocalRuntime` and renders `<Thread />`. That is the whole
integration.

## Decisions worth reading

**The dev server proxies `/chat` to FastAPI.** The browser only ever talks to one origin, which is
not cosmetic: same-origin means no CORS on the API, no preflight, and no `credentials: 'include'` to
get wrong later. Sage stays a plain JSON service that curl can still drive. See
[`vite.config.ts`](vite.config.ts).

**Only a finished exchange is stored.** A reply that is still streaming, was cancelled, or failed
has nothing worth replaying, so it is never written — and a half-written version already on disk is
removed. Writes are an upsert keyed on message id rather than a push, because `append` and `update`
can both arrive for the same message and the order stops mattering that way.

**Every read from localStorage is filtered.** A malformed turn would be replayed straight to the API,
which rejects the entire request with a 422 — so one corrupt entry would break every future message
until the user cleared their storage by hand. Anything that fails validation is dropped on read.

**A mid-stream failure is not an HTTP error.** Sage sends `200`, then reports the failure as an
`error` event in the body, because by the time the model fails the status line is already sent. The
adapter treats that event as the failure it is rather than as content.

**A cancelled run stays a cancellation.** When the user stops a reply, `fetch` rejects — and that is
re-thrown untouched rather than wrapped, so the library sees an abort instead of an error to show.

## Not here yet

One conversation, not many — there is no thread list, and clearing the browser's storage loses the
chat. That matches the API, which holds no conversation state and takes the history on every request.
When conversations move server-side, the change is the two adapters and nothing above them.
